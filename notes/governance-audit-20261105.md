## 与 Autoloop 的管理方法对照

对照公开仓库当前 AGENTS/SECURITY，以及已读源码快照 `22312e16419fc9f542a58044cfbb76f4aec80623`（package 1.1.1）。线上 main 文档持续更新，版本差异不当作本库缺陷。

| 方法 | 我们的现状 | 取舍与落地 |
| --- | --- | --- |
| 小内核、明确边界 | 总规则、项目与技能已有分工，入口重复 | 保留分工；AGENTS 负责操作，COLLABORATION 负责协作，START_HERE 只导航 |
| 可信规则与外部数据分离 | 旧 6 已有 | 保留；不照搬“所有外部文字不能进入提示词”作为普通研究禁令 |
| 挂起后恢复 | 已有 STATUS 约定，缺恢复动作 | 补等待原因、恢复条件、已有答复；只继续未完成步骤 |
| 事件去重与结果追溯 | 有普通 Git 历史和远端核验 | 补结果不明先读回；不引入 SQLite，不承诺外部操作恰好一次 |
| 失败止损 | 创意方法有停止迭代，通用工具重试不足 | 同一路径连续失败两次无新证据则诊断换路；保留可推进部分 |
| 并发分组 | 单一写入者过于笼统 | 所有同库直接写入串行，只读可并行；没有自动锁或调度器 |
| 按变动影响测试 | 有 7 项测试与目录检查，旧入口过度要求重建 | 文档查内容和引用；代码跑相关测试；卡片变才重建 INDEX |
| 少维护、无变化不报 | 已有轻量预算，首页持续追加超长 | 首页按任务导航，历史走 Git；有新证据才回写 |
| 工程专用限制 | 对方限定 Node、零运行依赖、无后台界面和发布机制 | 不移植为创作库全局限制；也不照搬 full 权限、自动上线或固定重试次数 |

Autoloop 文档也存在“总体要求全测试”与“纯文档按范围跳过”等层次，实际使用须按变更范围解释，不能用其规则更多来证明管理更好。其问人机制与访问级别也不等于宿主的硬权限屏障。这里只吸收适配的方法，未部署自动化。
