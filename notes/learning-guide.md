# 白话理解与学习顺序

## 这几个词怎么区分

| 名词 | 可以这样理解 | 你会怎么用 |
| --- | --- | --- |
| Git | 本机的存档和修改记录系统 | 改坏了，查历史和撤销某次修改 |
| GitHub | 放 Git 仓库、交流和协作的平台 | 上传资料库，换电脑克隆；给别人看 |
| 仓库 | 一个项目的文件和历史 | 这个资料库就是一个仓库 |
| 知识库 | 整理过、找得到的资料 | 项目卡片、笔记、来源和验证记录 |
| Agent | 能根据任务读取资料并使用工具的 AI 工作环境 | 帮你查卡片、做任务、记录结果 |
| Skill | 给 Agent 的可复用步骤说明，有时附脚本 | 明确什么时候做、怎么做、怎么验收 |
| MCP／CLI | Agent 调用工具的接口／命令入口 | 能否运行取决于宿主提供的真实能力 |
| RAG | 先检索相关片段，再把片段交给模型回答 | 大量文档时可升级；这个版本未接入 |

AGENTS.md 让支持它的宿主知道仓库规则；它本身没有模型，也不会把一个普通文件夹变成全自动服务。官方说明见 [AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)。Skill 的运行也依赖可用工具，见 [Build skills](https://learn.chatgpt.com/docs/build-skills)。

## 从你的三个主题推导出的实用方法

以下是结合公开仓库和你提供的视频标题整理的建议，不是未经读取的视频逐字总结。

**“收藏的神器值得装吗？”** 先写你当前任务和现有办法，再核对项目能带来什么增量。看文档只能证明宣称的用途；用真实输入跑一次、检查输出，才能给出有限范围内的可用结论。收藏但不安装完全合理。

**“工具太吵会影响 AI 吗？”** 不同工具可能有重复用途和冲突规则，带来选择成本。这个方向合理，但“AI 变笨全部由工具太多造成”不是已经证明的结论。任务描述、模型、上下文、权限和工具错误都可能影响结果。先只开放当前任务需要的入口，用相同任务比较成功率、修改次数、耗时和用量，再决定是否保留。

**“AI 为什么不翻知识库？”** 文件存在不代表 AI 能访问；能访问不代表有检索入口；有入口不代表会找到合适资料。解决顺序是：把仓库作为项目打开 → 明确入口文件 → 给卡片具体用途和排除条件 → 实测一次查找 → 把结果记录下来。Markdown 目录适合小库；资料多、检索变慢或关键词漏查时才考虑全文搜索或 RAG。

## 五天，每天完成一个可看见的结果

1. **第一天：**读 README 和这个表，自己用一句话解释 Git 与 GitHub。写入 notes/git-practice.md。
2. **第二天：**给笔记增加一段，再存档；看见两次提交的差别。
3. **第三天：**新增一个你真的有用的 GitHub 项目，填写卡片。写不出具体用途就停留在待核查。
4. **第四天：**让 AI 用卡片完成一个任务。判断产物是否符合你预先写的要求，记录失败也算学习结果。
5. **第五天：**上传到自己的 GitHub；从新目录克隆一次，确认文件和历史都在，再做一次查找练习。

分支和 PR 在你开始试验或协作时学习。Rebase、Stash、Worktree 可以等日常存档、同步和撤销熟练后再学。本轮没有核验两个视频的全部课程，因此这份顺序以 Git/GitHub 官方文档为依据。

## 我对复刻方案的判断

作者原版适合希望系统管理许多工具、安装范围、使用证据和恢复记录的人。对你的起步目标，最有价值的是流程和可核验记录，原版约两千行的核心维护脚本及额外生命周期模块会增加理解成本。

这个版本保留项目卡、短目录、按需读取、明确边界和实际结果记录。没有复制原版的事务、评级状态机、双语模板、多客户端适配和 Hook；这些在多人或自动化场景里可能有用，不能笼统称为无用代码。它们暂时不匹配你的最小起步需求。

最需要防止的是“为了维护库而维护库”。开始只收藏你近期真的会用的项目。每周找一张没有明确用途的卡片，补用途或改为已停用即可。项目越多不等于能力越强。
